## 1. 实际调用链

```text
Key-H
  -> Higress p1-strip-client-internal
  -> Higress p1-key-auth
  -> Higress p1-ext-auth
  -> 无状态 HMAC mapper
  -> ext-auth 白名单注入内部 Authorization: Bearer Key-L
  -> Higress p1-ai-proxy（无 apiTokens）
  -> LiteLLM Virtual Key
  -> 内网 Qwen3.6-27B
```

Key-L 由 `app_id` 和独立 32 字节根密钥按文档中的 `campus-ai-gateway/litellm-key/v1/` 规则派生。Key-L 未写入仓库、应用清单、mapper 日志或客户端响应。

## 3. LiteLLM 归属证据

P1 PostgreSQL 的 `LiteLLM_SpendLogs.api_key` 保存的是 LiteLLM Key Hash，而不是 Key-L 明文。实测 app-a、app-b 分别出现不同 Hash：

- app-a：由对应 HMAC Key-L 的 SHA-256 计算结果匹配；
- app-b：由对应 HMAC Key-L 的 SHA-256 计算结果匹配；
- 两个 Hash 不同，说明请求没有使用统一 Master Key。

## 4. 实施中的重要修正

最初尝试增加一个认证后删除客户端 `Authorization` 的 Transformer。实测插件执行顺序表明它会在 ext-auth 注入 Key-L 后再次删除该头，导致 LiteLLM 返回“无 API Key”。已删除该运行时插件，改为依赖：

1. key-auth 只接受配置的 Key-H；
2. ext-auth 必须成功，否则失败闭合；
3. ext-auth 成功响应仅允许 `Authorization` 和应用标识头进入上游；
4. ai-proxy 复用标准 Authorization 读取逻辑。
