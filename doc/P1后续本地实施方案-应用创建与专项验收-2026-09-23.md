# P1 后续本地实施方案：应用创建、专项策略验收与 Higress 配置发布

日期：2026-09-23  
适用环境：本地 Docker 独立 P1 环境 `api-gateway-p1-test`  目标域名：`ai-gateway-p1-test.local`

## 1. 文档目的

本方案承接《P1 阶段实施方案：应用级原生治理》和 P1-2 最小治理闭环验收，先完成本地可运行、可回滚、可重复验收的后续能力，再决定生产部署方式。

本轮不建设组织、后台、第二套额度账本、财务计费或自定义 AI 网关策略引擎；优先复用 LiteLLM 和 Higress 的原生能力。

- `scripts/Manage-P1Application.ps1` 已支持查询、策略更新、禁用、恢复、对账和 Key-H 双凭证轮换/退休。

- P1 LiteLLM 无宿主机推理端口，mapper 无宿主机端口，P0 保持 healthy。

## 4. 固定架构和职责

```text
管理员 CLI
  ├─ LiteLLM /key/generate /key/info /key/update /key/block
  ├─ Higress Admin API（p1-key-auth、allowlist、资源快照）
  ├─ apps.json（非敏感 app_id 与策略）
  └─ mapper reload/restart

客户端 Key-H
  -> Higress Consumer 认证
  -> ext-auth 调 mapper
  -> mapper 按 HMAC 派生 Key-L
  -> LiteLLM 执行 models/RPM/TPM/max_parallel_requests
  -> LiteLLM Provider / SpendLog
```

职责不可越界：

| 能力 | Higress | mapper | LiteLLM |
|---|---|---|---|
| 客户端 Key-H | 保存、验证、禁用、轮换窗口 | 不接收 | 不接收 |
| app_id 到 Key-L | 不负责 | HMAC 派生 | 只验证 Virtual Key |
| 模型权限 | 不负责应用级判断 | 不负责 | `models` allowlist |
| RPM/TPM/并发 | 只做入口级保护 | 不负责 | Virtual Key 原生策略 |
| Token/SpendLog | 入口指标可选 | 不记录 | Token、估算 Spend、请求归属 |
| 组织/财务计费 | 不在本轮 | 不在本轮 | 不在本轮 |

## 5. 应用创建实施方案

### 5.1 新增入口

已新增：`scripts/New-P1Application.ps1`

建议参数：

```text
-DisplayName
-Models
-RpmLimit
-TpmLimit
-MaxParallelRequests
-AppId（可选；未提供则生成 UUID）
-ChangedBy
-VerifyTimeoutSec（本地真实请求验证超时）
-RollbackAfterVerify（仅验收事务回滚）
```

脚本不得接受客户端自定义 Key-L；Key-L 始终由当前 P1 根密钥按 v1 HMAC 规则派生。

### 5.2 创建事务阶段

#### Prepare

1. 获取进程级/文件级锁，避免两个管理员同时修改应用清单。
2. 校验 `app_id` 格式和唯一性。
3. 校验模型非空、RPM/TPM/并发为正整数。
4. 校验模型存在于 LiteLLM 可用模型列表。
5. 创建本地事务记录，仅写入 app_id、目标策略、步骤状态，不写入任何 Key 明文。

#### Apply LiteLLM

1. 派生 Key-L，仅在内存中使用。
2. 调用 `/key/list` 或 `/key/info` 做幂等检查。
3. 不存在时调用 `/key/generate`，显式传入：
   - `key_alias = app_id`
   - 非空 `models`
   - `rpm_limit`
   - `tpm_limit`
   - `max_parallel_requests`
   - `metadata.app_id`
4. 再调用 `/key/info` 对账，确认策略完整。
5. LiteLLM 管理 API 调用带 `litellm-changed-by`。

#### Apply Higress

1. 生成随机 Key-H。
2. 更新 `p1-key-auth` 的 `defaultConfig.consumers`。
3. 将 app_id 加入 match rule 的 `allow` 列表。
4. Key-H 只写入本机忽略目录的一次性交付文件，不打印明文。
5. 先不对外宣传该应用，等待 mapper 清单更新完成。

#### Apply mapper 清单

1. 将 app_id、显示名、模型和策略写入 `config/p1-test/apps.json`。
2. 保留 `higress_key_env` 等非敏感字段。
3. 重启 mapper 或执行后续 reload 机制。
4. 通过 mapper `/healthz` 和直接拒绝用例确认新 app_id 已加载。

#### Commit

1. 使用新 Key-H 通过 Higress 发起真实 Qwen 请求。
2. 使用未授权模型确认 LiteLLM 返回 403。
3. 使用派生 Key-L 直接访问 Higress，确认返回 401。
4. 查询 LiteLLM `/key/info` 和应用清单，确认策略一致。
5. 写入不含密钥的成功事务记录和验收报告。

### 5.3 创建失败回滚

任何步骤失败都执行：

```text
禁用 Higress Consumer
-> 从 Higress allowlist 移除 app_id
-> 从 apps.json 移除未提交应用
-> mapper 重启并确认 app_id 不再授权
-> LiteLLM /key/block Key-L
-> 能安全删除时再调用 /key/delete，否则保留 blocked 证据
-> 恢复创建前的 Higress 快照
```

回滚要求：

- 回滚失败必须明确报告，不得静默忽略。
- blocked Key-L 不得重新成为有效凭证。
- 事务记录只保留 app_id、步骤、状态、错误类型和时间。
- 不在异常消息中打印请求头、Key-H、Key-L 或 Master Key。

### 5.4 创建完成标准

- 重复执行同一 app_id 为幂等成功，不生成第二个 Virtual Key。
- 创建成功后新 Key-H HTTP 200，错误 Key HTTP 401。
- 未授权模型 HTTP 403，Provider 不被调用。
- mapper 重启后新应用仍可调用。
- 任一中间步骤故障后没有未知有效应用凭证。
- P0 容器、卷、网络、密钥和配置不发生改变。

## 6. Higress 快照、发布和回滚

### 6.1 已新增脚本

- `scripts/Snapshot-P1Higress.ps1`
- `scripts/Publish-P1Higress.ps1`
- `scripts/Rollback-P1Higress.ps1`

### 6.2 快照范围

至少包含：

- `McpBridge/default`
- `Ingress/p1-ai-gateway-test`
- `WasmPlugin/p1-strip-client-internal`
- `WasmPlugin/p1-key-auth`
- `WasmPlugin/p1-ext-auth`
- `WasmPlugin/p1-ai-proxy`

### 6.3 脱敏规则

原始 API 返回可能包含 Key-H，不能直接写入 Git。快照分两种：

1. 运行时原始快照：只写 `runtime/p1-test/higress/snapshots/`，由 `.gitignore` 排除。
2. 审核快照：将 credentials 替换为 `<REDACTED>`，附 SHA-256 指纹和资源版本，可提交 Git。

### 6.4 发布流程

```text
读取声明式 apps.json / resources.json
-> 获取当前 Higress 原始快照
-> 生成脱敏审核快照
-> 应用目标资源
-> 等待资源版本生效
-> 语义比较目标与实际状态
-> 运行 P1 技术闸门
-> 成功后保留新快照
```

发布必须使用资源版本，不能无条件覆盖其他管理员刚提交的修改。

### 6.5 回滚标准

```text
选择上一个原始快照
-> PUT 资源并等待生效
-> 验证 Key-H、allowlist、ext-auth、upstream
-> 执行真实请求和失败闭合测试
-> 记录 rollback 结果
```

Key-H 双凭证窗口期间，快照必须能保留两把凭证；否则重新 bootstrap 可能意外提前撤销旧 Key-H。

## 7. LiteLLM 专项策略验收

### 7.1 TPM（已通过）

- App B 临时设置低 TPM。
- LiteLLM 重启清空旧窗口。
- 发送已知超过阈值的请求。
- 预期 429，且不触达 Provider。
- 恢复原值并 Reconcile。

实际报告：`runtime/p1-test/reports/p1-protocol-matrix-20260923-104258.md`，App B `tpm_limit=1` 返回 HTTP 429。

### 7.2 最大并发（已通过本地单副本验收）

- App B 设置 `max_parallel_requests=1`。
- 并发发起两个长请求或 SSE 请求。
- 预期只有一个进入 Provider，另一个被限制或等待。
- App A 同时请求必须不受影响。

本地单副本只能证明单实例行为；多副本生产需要 Redis 或 LiteLLM 官方共享状态方案。本次结果为并发请求 HTTP `[429,200]`。

### 7.3 SSE（已通过）

- 使用 `/v1/chat/completions` 和 `stream=true`。
- 验证 `text/event-stream`、多个 chunk、`[DONE]`。
- 验证响应头不泄露 Key。
- 验证 SpendLog 有 token 和 model。

实际结果：`text/event-stream`、`[DONE]` 和 HTTP 200 均通过。

### 7.4 Responses（已通过）

- 调用 `/v1/responses`。
- 验证 Qwen callback 转换结果。
- 验证正常响应、失败响应和 SpendLog 归属。

本地 Qwen Responses 请求 HTTP 200；兼容逻辑复用 `gateway/litellm/callback/qwen_responses_compat.py`。

### 7.5 Tools（已通过网关透传）

- 发送 function tool 请求。
- Provider 支持时验证 tool call 结构和后续请求。
- Provider 不支持时记录为模型能力限制，不在网关增加伪造兼容逻辑。

本地 function tool 请求 HTTP 200，未新增工具转换层。

### 7.6 SpendLog（已通过）

通过 SHA-256(Key-L) 查询 `LiteLLM_SpendLogs.api_key`，验证：

- model
- prompt_tokens
- completion_tokens
- total_tokens
- spend
- start/end time
- error/status

不能查询或输出 Key-L 明文。Spend 仅为 LiteLLM 估算值，不用于财务结算。

实际报告验证 App A `rows/messages/responses=61|61|61`，并通过 SHA-256(Key-L) 查找，报告没有密钥明文。

## 10. 本轮默认决策

以下决策沿用此前确认，不再阻塞本地开发：

1. 一个客户端应用对应一个 Higress Consumer。
2. Key-L 继续使用 HMAC 无状态派生。
3. LiteLLM 负责模型、Token、RPM、TPM、并发、SpendLog 和估算 Spend。
4. Higress 负责入口认证、Consumer、网络入口、WAF 和粗粒度保护。
5. 本地日志正文保留 7 天，运行时数据不提交仓库。
6. 测试模型继续使用 `my-qwen3.6-27b`。
7. 本地可重启 P1 容器，但不重启或修改 P0。

- TPM、最大并发、SSE、Responses、Tools 和 SpendLog 有实际报告。

- 所有报告不含 Key-H、Key-L、Master Key 或 Provider Key 明文。
