# 当前两个项目的合并架构分析

> 分析日期：2026-09-20  
> 范围：当前工作区代码、Git 元数据、Docker Compose、运行时配置快照、上游源码快照与离线测试。  
> 原则：本文只做分析与规划，不移动、删除或重写业务代码。

## 1. 结论摘要

当前仓库并不是两个可直接合成为单一业务应用的自研项目，而是一个校园统一 AI 网关集成工程，引用并编排两个职责不同的上游基础设施产品：

- **Higress**：边缘/API 网关，负责入口、路由、TLS、WASM 鉴权、流量治理和 Envoy 指标。
- **LiteLLM**：AI 模型网关，负责 OpenAI 兼容协议、多供应商适配、模型别名、Virtual Key、团队、模型权限、预算和用量。

推荐目标不是把 Higress 与 LiteLLM 重写或合并为一个进程，而是：

1. 将本项目拥有的部署、配置、扩展、测试、脚本和未来平台应用整理为一个 Monorepo；
2. 将 Higress 与 LiteLLM 保留为独立的运行时组件和受版本锁定的第三方依赖；
3. 在产品层统一校园身份、组织、角色、应用、API Key、额度、账单、审计和门户；
4. 保留 LiteLLM 的模型代理职责与 Higress 的边缘网关职责，不直接修改或复制其内部领域模型。

因此，**适合统一为一个产品和一个受控工程，但不适合合并成一个单体服务。**

## 2. 当前两个项目的识别结果

| 项目 | Higress | LiteLLM |
| --- | --- | --- |
| 本地路径 | `sources/higress-src/` | `sources/litellm-src/` |
| 上游仓库 | `github.com/alibaba/higress` | `github.com/BerriAI/litellm` |
| 当前源码提交 | `dc0999326b1a8df4269c13d0cf6ee2b725259f6e` | `47b15ffb677902fc4550a4471b82e09f77ec77d7` |
| 项目定位 | 边缘/API 网关 | AI 模型代理与控制面 |
| 当前运行方式 | 远程 `all-in-one` 镜像 | 固定上游镜像 digest 上叠加本项目补丁 |
| 当前是否从本地源码构建 | 否 | 否；仅构建自定义补丁镜像 |
| 数据库 | 当前不使用本项目 PostgreSQL | PostgreSQL 16 |
| 管理入口 | Higress Console，`:8001` | LiteLLM UI，`:4000/ui/` |

### 2.1 Higress

- **项目定位**：通用云原生 API Gateway / Envoy 网关。
- **主要功能**：HTTP/HTTPS 入口、路由、服务发现、WASM 插件、边缘鉴权、重试、流量治理和指标导出。
- **技术栈**：Go、Envoy、Istio/Kubernetes 风格资源、WASM。
- **前端框架**：Higress Console；不是本项目自研前端。
- **后端框架**：Go 控制面与 Envoy 数据面。
- **数据库**：当前 Compose 部署不依赖本项目 PostgreSQL。
- **认证方式**：当前专用路由使用 `key-auth` WASM；普通 `/v1` 路由不启用 Higress Key Auth，而是透传到 LiteLLM。
- **API 设计**：管理侧是 Ingress、McpBridge、WasmPlugin 等资源；业务侧转发 OpenAI 兼容 `/v1/*`。
- **配置管理**：当前实际资源位于 `runtime/higress/`，混有声明配置、控制台生成字段、状态与敏感信息。
- **构建与部署**：上游支持 Go 构建；本项目 `deploy/docker-compose.yml` 直接拉取 `higress/all-in-one:latest`。
- **核心目录**：上游 `cmd/`、`pkg/`、`plugins/`、`api/`；本项目关联运行配置为 `runtime/higress/`。

### 2.2 LiteLLM

- **项目定位**：统一多供应商模型的 AI Gateway / LLM Proxy。
- **主要功能**：模型别名、供应商协议适配、OpenAI 兼容 API、Virtual Key、用户/团队/组织、模型权限、预算、限流和 Spend Log。
- **技术栈**：Python、FastAPI、Pydantic、Prisma Python、PostgreSQL。
- **前端框架**：React 19、Next.js 16、TypeScript、Tailwind；源码在 `sources/litellm-src/ui/litellm-dashboard/`。
- **后端框架**：FastAPI Proxy。
- **数据库**：PostgreSQL 16；模型定义在 `sources/litellm-src/schema.prisma`。
- **认证方式**：master key、Virtual Key、JWT/SSO、User/Team/Organization 权限模型。
- **API 设计**：对外 OpenAI 兼容 `/v1/chat/completions`、`/v1/responses`、`/v1/embeddings`、`/v1/models` 等；另有管理 API。
- **配置管理**：`config/litellm.yaml`、环境变量和数据库管理对象共同参与。
- **构建与部署**：`gateway/litellm/Dockerfile` 从固定 LiteLLM 镜像 digest 构建，复制回调、应用流式补丁并运行构建期测试。
- **核心目录**：上游 `litellm/`、`schema.prisma`、`ui/litellm-dashboard/`；本项目扩展在 `gateway/litellm/`。

## 3. 当前实际架构与调用关系

主部署编排位于 `deploy/docker-compose.yml`：

```text
Client / SDK
  → Higress :8080 / :8443
  → LiteLLM :4000
  → Provider API
       ↘ PostgreSQL 16

Higress metrics → Prometheus → Grafana
```

当前存在两条入口语义：

| 入口 | 认证与归属 | 风险/说明 |
| --- | --- | --- |
| 普通 `/v1` 路由 | 客户端 LiteLLM Virtual Key 透传到 LiteLLM | 能保留 LiteLLM Key、Team、模型权限和用量归属 |
| `ai-test.local` 专用路由 | Higress Consumer Key 验证后，`ai-proxy` 改写为 LiteLLM 下游凭据 | LiteLLM 无法自然按原始 Higress Consumer 区分用量；不应直接用作多租户生产入口 |

当前模型和 Provider 映射由 `config/litellm.yaml` 维护；包含 DashScope、校园 AIGC、DeepSeek 和 Agnes 等上游。`gateway/litellm/` 中的本项目自定义逻辑包括：

- 流式 Responses 中空 `choices` 的三处边界保护；
- 仅对 `my-qwen3.6-27b` Responses 请求生效的 Qwen system/developer 指令兼容回调；
- 针对固定上游镜像的构建期回归测试和回滚 Compose 覆盖。

这些扩展属于 LiteLLM 一侧，不应迁移到 Higress。

## 4. 重复功能和重叠代码

不存在两个自研业务系统之间的代码重复；存在的是两个基础设施组件边界相邻而造成的局部功能重叠。

| 项目项 | 判断 | 事实 |
| --- | --- | --- |
| 用户系统 | 不重复 | LiteLLM 有 User/Team/Organization；Higress 无校园用户域 |
| 权限系统 | 局部重叠 | Higress 控制入口允许/拒绝；LiteLLM 控制 Key、模型、组织、团队和预算 |
| 数据库模型 | 不重复 | 只有 LiteLLM 使用本项目 PostgreSQL |
| OpenAI API | 分层复用 | Higress 代理 `/v1/*`；LiteLLM 负责实现和供应商适配 |
| 模型管理 | LiteLLM 为主 | 当前模型别名和上游配置在 `config/litellm.yaml` |
| AI Gateway | 两层职责不同 | Higress 是边缘网关；LiteLLM 是模型网关 |
| 管理后台 | 两个后台但资源不同 | Higress 管路由/插件；LiteLLM 管模型、Key、团队、用量和日志 |
| 前端组件 | 不应复用 | 两套都是上游产品内部实现 |
| 监控 | 互补 | Prometheus/Grafana 当前主要采 Higress/Envoy 指标；LiteLLM 保存业务用量 |

结论：不能把两个管理后台、两套认证机制或两个网关组件简单视为重复代码。真正需要统一的是产品层的身份、组织、应用、额度、账单和运营入口。

## 5. 当前冲突与工程问题

### 5.1 身份和 API Key 双轨

普通入口使用 LiteLLM Virtual Key；专用 Higress 路由使用另一套静态 Consumer Key，并改写为 LiteLLM 下游凭据。这会造成：

- 身份来源不统一；
- 专用入口的 LiteLLM 用量归属不够精细；
- 运维凭据被用于转发的边界不清；
- 未来难以统一组织、应用、模型权限与审计。

### 5.2 配置权威来源不清

- LiteLLM 模型可能同时来自 YAML 和数据库；当前需确认 `store_model_in_db: true` 的最终合并和优先级语义。
- Higress 实际路由位于被 Git 忽略的 `runtime/higress/`。
- 运行时目录混有可复建资源、Secret、`managedFields`、`resourceVersion`、状态和诊断产物。

### 5.3 版本漂移

- LiteLLM 自定义镜像以固定 digest 为基线，本地 `sources/litellm-src` 仅为参考快照，不是 Docker 构建输入。
- Higress 使用 `latest` 标签，本地源码却固定在一个 commit；两者尚无明确可验证映射。
- 因此不能仅凭 `sources/` 中的代码推断线上镜像的实际行为。

### 5.4 Git 元数据问题

根仓库索引中 `sources/higress-src` 和 `sources/litellm-src` 是 `160000` gitlink，但仓库没有 `.gitmodules`。`git submodule status` 当前会失败。新克隆者无法可靠恢复上游源码目录。

### 5.5 当前工作树迁移未提交

当前工作区已经把根目录 Compose 移至 `deploy/`，把旧 `config/litellm-patch/` 移至 `gateway/litellm/`；Git 索引仍保留旧路径删除与新目录未跟踪状态。后续应将这次目录迁移作为独立、可验证的提交处理。

### 5.6 安全问题

Compose 中仍有面向本地测试的固定数据库密码和 LiteLLM master key；被忽略的 Higress 运行目录还包含敏感配置。生产化前应迁移至环境级密钥管理、清理可见凭据，并轮换已有长期值。

## 6. 方案比较

### 方案 A：继续保持两个完全独立项目

**优点**

- Higress 和 LiteLLM 可以独立升级、扩缩容和故障隔离。
- 组件边界符合原生设计，不需要维护 Go/Envoy/Python 的大分叉。

**缺点**

- 两个控制台、两套配置、两种公开入口身份语义会持续割裂运营体验。
- 用户、组织、应用、额度和账单没有统一权威。
- 未来校园 SSO、审批、成本中心和审计无法仅靠其中任一组件完成。

**长期维护成本与适配性**

保留两个运行组件是合理成本；长期维护两个上游源码副本、两个公开认证方案和两个面向用户的管理入口则是不合理成本。该方案仅适合短期验证，不适合作为最终校园 AI 平台。

### 方案 B：一个代码仓库，保留多个应用和组件

这是推荐方案，但 Monorepo 的范围应是本项目拥有的代码，不是将两套上游源码变成自研应用。

适合统一管理的内容：

- 部署编排、配置模板、LiteLLM 扩展、初始化脚本、测试、监控、文档；
- 后续 Portal、Control API、SDK、领域契约和 UI；
- 锁定版本的 Higress/LiteLLM 外部依赖。

不适合：

- 把完整 Higress/LiteLLM 源码搬进 `apps/` 后长期分叉；
- 强行合为一个构建产物或单一语言栈；
- 让新平台直接写 LiteLLM 全部内部表。

### 方案 C：真正合并成一个统一应用

如果“统一应用”指单进程、单 ORM、单数据库模型并替换两个基础设施：**不建议**。

Higress 的 Envoy/控制面模型和 LiteLLM 的 Python 供应商适配、流式协议、Prisma 数据模型均是成熟且复杂的能力；重写风险远高于收益。

如果“统一应用”指一个统一产品身份、统一组织/权限、统一 API Key 生命周期、统一账单、统一 Portal：**应该做，且可行**。物理运行时仍保留 Higress + LiteLLM。

## 7. 推荐目标架构

当前阶段不应创建没有实现内容的 `apps/web`、`apps/admin`、`apps/api` 空目录。推荐先整理已有工程，并为未来平台功能预留边界：

```text
API网关/
├── deploy/                         # Compose、部署清单、环境编排
├── config/
│   ├── litellm/                    # 模型、Provider、LiteLLM 配置
│   ├── higress/                    # 脱敏的期望路由/插件模板（新增）
│   └── monitoring/                 # Prometheus/Grafana
├── gateway/
│   └── litellm/                    # Dockerfile、patch、callback、回滚、回归测试
├── scripts/
│   ├── bootstrap/                  # Higress 初始化
│   ├── export/                     # 导出、脱敏、差异检查
│   └── diagnostics/                # 可复用诊断工具
├── tests/
│   ├── unit/
│   ├── integration/
│   ├── live/                       # 明确标记：可能产生费用
│   └── benchmark/
├── runtime/                        # Git 忽略：实例状态、报告、抓包、临时产物
├── third_party/
│   ├── higress/                    # 正式 submodule 或可重复获取的锁定源码
│   └── litellm/
├── docs/
├── apps/                           # 平台建设时再加入
│   ├── portal/                     # 统一开发者/管理员门户
│   └── control-api/                # 校园领域控制面
└── packages/                       # 有第二个消费者时再提取
    ├── contracts/
    ├── sdk/
    └── ui/
```

迁移原则：

| 当前路径 | 目标 | 原则 |
| --- | --- | --- |
| `deploy/` | 保留 | 当前已完成初步迁移，不退回根目录 |
| `gateway/litellm/` | 保留 | 是本项目真正维护的扩展代码 |
| `config/litellm.yaml` | `config/litellm/` | 后续按环境拆分，先不改变语义 |
| `config/monitoring/` | 保留 | 当前边界合理 |
| `runtime/higress/` | 保留为运行实例目录 | 不直接提交 |
| `runtime/higress` 中脱敏资源 | `config/higress/` | 由导出/清洗脚本生成模板 |
| `test/` | `tests/` | 有统一入口后再迁移 |
| `sources/` | `third_party/` 或保留 | 先修复 gitlink/.gitmodules |

## 8. 数据库与领域模型统一方案

LiteLLM 当前 schema 已有 User、Organization、Team、Project、VerificationToken、ProxyModel、Budget、SpendLogs、AuditLog 等模型。这些是 AI 网关运行时模型，不能直接承担校园业务系统的全部主数据职责。

| 领域对象 | 权威系统 | 与 LiteLLM 的关系 |
| --- | --- | --- |
| User | 校园 Identity / Control API | 映射为 LiteLLM User 或 SSO 身份 |
| Organization / Tenant | 校园组织域 | 映射为 LiteLLM Organization/Team |
| Role / Permission | 校园 RBAC | 投影到 LiteLLM 管理角色、Team、Model、Key 权限 |
| Application / Project | Control API | 映射为 LiteLLM Project 或受控 Team |
| API Key | 统一 Key 生命周期服务 | LiteLLM Virtual Key 是实际推理授权载体 |
| Provider Credential | 平台密钥管理 | 注入 LiteLLM，不进入前端和普通业务表 |
| Provider / Model | 平台模型目录 | 发布到 LiteLLM YAML 或管理 API；必须单写入口 |
| Usage / Token | LiteLLM Spend Log | 原始计量来源，导入不可变账本 |
| Quota | 平台额度策略 | LiteLLM 承担在线限制；平台承担规则、审批和结算 |
| Billing | 平台账单域 | 不能只依赖可聚合 `spend` 字段 |
| Audit | 统一审计事件流 | 保留两侧原始审计，使用关联 ID 聚合 |
| System Config | 分组件管理 | 不追求一个巨型 YAML |

关键原则：

1. 不直接修改 LiteLLM 内部 Prisma schema 来承载校园业务域。
2. Portal 不直接写 LiteLLM 数据库；应通过受控管理 API 或同步服务操作。
3. 新增模型只能有一个写入口，不能同时修改 YAML、LiteLLM API 和数据库。
4. 账单应基于不可变事件、模型价格版本、流式中断和重试结果结算；`spend=0` 不能证明调用免费。

## 9. 用户、认证、权限统一方案

推荐的最终链路：

```text
Campus OIDC / SSO
  → Portal / Control API
  → User、Organization、Role、Application、API Key 生命周期
  → LiteLLM User / Organization / Team / Project / Virtual Key
  → Higress 负责边缘 JWT/OIDC、TLS、WAF、路由和基础限流
  → LiteLLM 执行模型级权限、预算和用量归属
```

建议：

- 校园 IdP 是唯一用户身份来源；LiteLLM 的 `sso_user_id` 或等效字段保存外部 subject 映射。
- 校园组织是 Organization/Tenant 的权威，LiteLLM Organization/Team 为投影。
- 一个校园应用映射为 LiteLLM Project 或受控 Team。
- 对外只暴露一种产品 API Key；其背后关联应用、组织、模型范围、额度、过期和 LiteLLM Virtual Key。
- Higress Consumer Key 不再作为公开产品 Key，只用于可信内部调用或过渡测试。
- LiteLLM master key 只能用于运维管理，不能作为终端用户的常规转发凭据。
- 当前 `ai-test.local` 专用路由应被明确限制为测试或可信内部场景，直到统一身份链路完成。

## 10. API / AI Gateway 统一方案

对外统一维持 OpenAI 兼容 API：

```text
/v1/models
/v1/chat/completions
/v1/responses
/v1/embeddings
/images/generations
```

| 层 | 保留职责 | 不承担的职责 |
| --- | --- | --- |
| Higress | TLS、边缘认证、WAF、连接保护、基础限流、路由、网络级故障处理、指标 | Provider 协议适配、模型授权账本 |
| LiteLLM | 模型别名、Provider 适配、Virtual Key、模型权限、Token/Spend、模型级 fallback | 校园用户主数据、复杂业务账单、TLS |
| Control API | 用户/组织/应用、审批、Key 生命周期、额度策略、账单、审计聚合 | 代理所有推理流量 |
| Portal | 统一用户操作入口 | 直接读写 LiteLLM 内部表 |

重试边界应唯一：

- 网络连接层有限重试：Higress；
- 模型/Provider 级 fallback、重试、路由：LiteLLM；
- 业务幂等、额度预占和账单结算：Control API。

不得让 Higress 与 LiteLLM 为同一非幂等请求无限叠加重试。

## 11. 前端和管理后台统一方案

当前仓库没有两套自研 Web/Admin，因此没有可直接合并的前端代码。

现有后台应定位为基础设施运维后台：

- LiteLLM UI：模型、Key、Team、Usage、Logs 的应急与底层运维入口；
- Higress Console：路由、WASM、证书、插件的应急与底层运维入口。

未来 `apps/portal` 应统一日常产品操作：

- 开发者：API Key、模型目录、用量、额度、SDK 示例；
- 组织管理员：成员、应用、授权范围、预算、审批；
- 平台管理员：Provider、模型发布、策略、审计、账单；
- SRE：从 Portal 跳转至 Higress/LiteLLM 原生后台处理低层故障。

不要抽取 LiteLLM Dashboard 或 Higress Console 的内部组件作为本项目共享 UI；适合共享的是未来 Portal、Control API 与 SDK 的契约和设计系统。

## 13. 合并过程中最大的风险

1. 将统一误做成重写 Higress 或 LiteLLM。
2. 将 LiteLLM 内部数据库误当成校园主数据和账单主库。
3. 同时写 YAML、LiteLLM 管理 API、LiteLLM 数据库，导致模型和权限漂移。
4. 将现有专用 Higress 路由的凭据改写机制推广到多租户生产入口。
5. 两层重试叠加，产生重复调用和重复计费。
6. 提交整个 `runtime/`，泄露 Secret、证书、消费者凭据和控制台状态。
7. 使用 Higress `latest` 却假定本地源码 commit 等于运行版本。
8. 未修复 `.gitmodules` 即删除或移动上游源码快照。
9. 将 benchmark 的 `main-stable` LiteLLM 结论误用于定制生产镜像。
10. 未备份、未对账 PostgreSQL 就迁移用户、Key、预算和用量。

## 14. 最终需要删除或废弃的旧代码

不应删除 Higress 或 LiteLLM 本体。应在满足回滚周期后处理：

- 根目录旧 Compose、旧 `config/litellm-patch/` 路径及所有旧引用；
- 被跟踪的 `__pycache__/`、`.pyc`；
- 不可复用抓包、HTML、SSE、二进制样本，迁移至 `runtime/diagnostics/` 或归档；
- 公开使用的 Higress Consumer Key 双轨入口；
- 依赖手工控制台状态的 Higress 部署流程；
- 无 `.gitmodules` 的孤立 gitlink 状态；
- 旧文档中失效的路径、版本与未验证结论。

## 15. 推荐实际执行顺序

1. 提交或暂存当前 `deploy/`、`gateway/litellm/` 的已有迁移，结束工作树与 Git HEAD 的双状态。
2. 固定 Compose 项目名、网络名和卷名，避免目录迁移影响既有 PostgreSQL 卷。
3. 建立 Higress 镜像、LiteLLM 镜像、上游源码 commit、补丁哈希的版本清单。
4. 修复 `sources/` 的 gitlink 元数据；使用正式 submodule 或带 commit 校验的获取脚本。
5. 从 `runtime/higress/` 提取脱敏声明模板至 `config/higress/`，并创建初始化、导出和差异检查脚本。
6. 修正 `.env.example`，将生产凭据迁移至密钥管理系统并轮换长期测试值。
7. 建立统一测试入口，明确区分 unit、integration、live、benchmark。
8. 设计校园 Identity、Organization、Application、Key、Quota、Billing 的领域模型与同步契约。
9. 建设 Portal 与 Control API，通过 LiteLLM 管理 API 集成，而不是直接写其内部表。
10. 身份和 Key 灰度迁移完成后，废弃专用双 Key 路由与旧运维流程。
