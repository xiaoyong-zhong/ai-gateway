# P1-2 最小应用治理闭环验收

日期：2026-09-23  
环境：本地 Docker 独立 Compose 项目 `api-gateway-p1-test`  
目标域名：`ai-gateway-p1-test.local`  
结论：**最小闭环及本地应用生命周期验收通过；LiteLLM 原生 Audit 仍待生产版本/授权确认**

## 1. 本次验收范围

本次只验收复用 LiteLLM 和 Higress 原生管理接口的最小应用治理闭环，不扩展组织、后台、Token 钱包或财务计费：

- `Get`：查询应用对应 LiteLLM Virtual Key 的非敏感状态；
- `SetPolicy`：更新模型 allowlist、RPM、TPM、最大并发和 metadata；
- `Disable`：先从 Higress `p1-key-auth` allowlist 移除 Key-H，再调用 LiteLLM `/key/block`；
- `Enable`：先调用 LiteLLM `/key/unblock`，再恢复 Higress Key-H allowlist；
- `Reconcile`：检查 `key_alias`、模型和策略是否仍与应用标识一致。

实现入口为 [`Manage-P1Application.ps1`](../scripts/Manage-P1Application.ps1)。脚本只在本机通过 Docker Compose 管理面调用 LiteLLM 和 Higress，不发布新的网络端口，不把 Key-H、Key-L、Master Key 或派生根密钥写入日志；轮换产生的新 Key-H 仅写入被 `runtime/` 忽略的本机一次性交付文件。

## 3. 当前边界和未完成项

本次以 A/B 应用策略闭环为基础，已补充完整应用生命周期的本地验收。当前未完成项如下：

1. 应用创建命令：`New-P1Application.ps1` 已把“生成 Key-H、写入 Higress Consumer、创建 LiteLLM Virtual Key、发布 allowlist、mapper 重启和真实请求验证”封装成事务；持久化测试应用 `app-3f9c7b21-6b5e-4d8a-9c31-2e7a6f5b4c10` 已完成全 P1 容器重启后的调用和同声明重复执行幂等验收。
2. Key-H 轮换的缓存边界：Higress 管理 API 删除旧 credential 后，运行中的 key-auth 插件仍可能保留旧缓存；`RetireKeyH` 因此强制要求 `-RestartHigress`。生产应改为可观测的滚动更新/实例替换，而不是无计划重启。
3. 运行时变更持久化：已增加 `Snapshot-P1Higress.ps1`、`Publish-P1Higress.ps1`、`Rollback-P1Higress.ps1`；原始快照只写被忽略的 `runtime/p1-test/higress/snapshots/`，发布前自动备份，发布和回滚均已本地执行通过。
4. 完整策略证据：`Test-P1ProtocolMatrix.ps1` 已实际通过 TPM=1 的 HTTP 429、最大并发 `[429,200]`、SSE、Responses、Tools 和 SpendLog；报告为 `runtime/p1-test/reports/p1-protocol-matrix-20260923-104258.md`。
5. 操作审计：CLI 有 `litellm-changed-by` 请求头，但尚未验收 LiteLLM Audit 的字段、保留期和脱敏策略。

补充验证：P1 LiteLLM 已打开原生 `store_audit_logs` / `LITELLM_STORE_AUDIT_LOGS=true`，但当前本地 LiteLLM 镜像的 `create_audit_log_for_update` 还要求 `premium_user is True` 才写入 `LiteLLM_AuditLog`。本地实测策略更新、block/unblock 后该表仍为 0 行。因此本地不能把“配置打开”当作审计已完成，也没有新增自定义审计表；生产需先确认 LiteLLM 版本/授权能力，再决定是否复用其原生 Audit，或仅保留管理面访问日志作为证据。

## 4. 结论

P1-2 的“查询—策略更新—禁用—恢复—对账—Key-H 轮换—应用创建事务—配置快照”能力可以作为后续开发基线。持久化应用已完成全 P1 容器重启后的 200/403 验证，重复执行也已通过幂等检查。P1 全量技术闸门已通过；后续主要是结项文档以及上线前确认 LiteLLM 原生 Audit 的版本/授权能力。
