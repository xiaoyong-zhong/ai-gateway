# 校园统一 AI 网关项目现状与 PRD 完成度分析

基准文档：`doc/校园统一AI网关产品需求文档.md`  
分析日期：2026-09-20  
分析范围：当前仓库实际代码、部署配置、运行时 Higress 配置、测试、数据库元数据和运行容器。

## 1. 当前项目整体判断

以完整 PRD 为基准，当前整体完成度约 **20%–25%**；若只看 Higress → LiteLLM → PostgreSQL → 多上游模型的技术验证链路，完成度约 **60%**。

当前处于 **POC / 本地集成验证阶段**，尚未进入可交付的校园统一 AI 平台 MVP 阶段。

已经具备继续迭代的基础：主链路可运行、模型别名可用、数据库已初始化、基础监控和自动化测试存在。但用户、组织、应用、权限、额度账本、管理后台、模型发布、审计和产品看板等核心平台能力尚未形成闭环。

本次实际核验：

- 主、监控、压测 Compose 均通过语法校验。
- Higress、LiteLLM、PostgreSQL、Prometheus、Grafana 容器正在运行。
- 两个模型列表入口均可在授权后返回 8 个模型，匿名访问返回 401。
- 数据库存在 1 个用户、1 个团队、9 个 Key、1,290 条用量日志；组织和审计业务数据为空。
- 离线测试通过：13 个 Python 单元测试、4 个 Mock 测试、6 个流式补丁测试、7 个 Qwen 兼容测试。
- 未执行新的真实模型推理调用，历史文档中的真实调用结果不作为本次新验收证据。

## 3. 已完成的核心能力

- Higress 与 LiteLLM 双层网关可运行。
- 已接入 DashScope、校园 AIGC、DeepSeek、Agnes 等上游示例。
- 已提供 Chat Completions、Responses、Embeddings 基础入口。
- PostgreSQL 已持久化 LiteLLM 的 Key、团队和用量日志。
- Higress Key Auth 可拒绝匿名访问。
- Qwen Responses 前置消息兼容和空 `choices` 流式补丁已通过容器内回归测试。
- Prometheus + Grafana 已能展示入口 QPS、状态码、上游请求、超时、重试和活跃请求。
- 已具备隔离 Mock 上游、k6 压测和基础离线回归设施。

## 4. 部分完成与具体问题

### 4.1 双入口导致身份模型不一致

默认 `/v1` 路径把客户端 Key 透传给 LiteLLM；`ai-test.local` 路径由 Higress 静态 Key 认证后，再替换为 LiteLLM 主密钥。后者无法把真实调用方传给 LiteLLM，不能实现按用户、应用和组织的额度、模型权限及审计。

### 4.2 模型配置不是模型管理

YAML 只能完成静态别名映射，不能完成渠道、部署、能力、价格、健康、发布和回滚。`qwen3.7-flash` 当前映射到 `qwen3.5-ocr`，除非这是有意别名，否则属于高风险配置错误。

### 4.3 计量不是 PRD 账本

现有 SpendLog 可以记录 Token、时间和 LiteLLM 估算费用，但缺少组织/应用/Key 多层额度、预占、释放、补偿、周期切换和价格版本。数据库中虽有 Key 预算字段，但没有项目自有预算账本。

### 4.4 日志与隐私规则冲突

`config/litellm.yaml` 开启了 `store_prompts_in_spend_logs: true`。当前数据库中有大量响应字段记录，这与 PRD“正文默认不记录、正文独立授权、短期留存”的要求冲突，应先确定数据保护策略。

### 4.5 监控不是产品看板

现有 Grafana 主要是 Envoy/Higress 基础设施指标，不能按用户、组织、应用、逻辑模型、渠道下钻，也没有 PRD 要求的业务成功率、Token/费用口径、告警状态机和通知闭环。

## 7. 技术债务与架构风险

1. 主密钥、数据库密码和测试消费者 Key 在部署或测试文件中明文出现，应立即轮换。
2. LiteLLM、Higress 控制台和网关端口存在过宽绑定；Grafana 开启匿名 Viewer。
3. Higress `key-auth`、`ai-proxy` 使用 `FAIL_OPEN`，插件异常时可能放行。
4. AI Proxy 使用 LiteLLM 主密钥替换调用者身份，破坏按调用方治理。
5. `runtime/` 被 `.gitignore` 忽略，却承载真实 Higress 路由、插件和证书，仓库无法从零可靠复建。
6. 文档仍引用已删除的根目录 Compose 和旧补丁路径，与当前 `deploy/`、`gateway/` 结构漂移。
7. `drop_params: true` 可能静默丢弃不支持字段，与 PRD 的显式能力拒绝相冲突。
8. Envoy 网络重试不是模型级 Fallback，可能放大非幂等调用和成本。
9. 测试存在已知漏检：普通双网关测试可能接受空 JSON，Mock 错误模型测试集合未完整执行。
10. `latest`、`main-stable` 等浮动镜像标签使环境不可复现。

## 8. 下一阶段路线图

### P0：必须先完成

1. 冻结 PRD Q01–Q12 中影响架构的决策，形成权限矩阵、计量口径、错误码和领域模型。
2. 轮换所有已暴露凭证，接入 Secret 管理，固定镜像，关闭公网管理端口，提交脱敏可复建配置。
3. 确定唯一正式 API 入口，禁止静态 Higress Key 直接替换为 LiteLLM 主密钥。
4. 新建管理后端、业务数据库迁移和配置发布机制，不再以手工修改运行时 YAML 作为主流程。
5. 修复认证错误码、静默参数丢失和测试假阳性，建立可重复的最小集成验收环境。

### P1：核心产品能力

1. 对接校园 SSO，实现用户、组织、应用、角色、Key、IP 策略。
2. 实现供应商、渠道、部署、模型能力、价格、健康和草稿/发布/回滚。
3. 实现多层额度、Redis 原子预占、RPM/TPM/并发、周期结算和价格版本。
4. 实现候选渠道、权重/优先级、Fallback、熔断、流式边界和会话粘性。
5. 实现请求/尝试链、审计、脱敏日志、业务看板和告警状态机。
6. 实现最小管理员后台和开发者工作台。

### P2：产品完善

- OAuth/订阅资源管理。
- 模型广场、兼容性清单、客户端教程、公告和 FAQ。
- 内容审计、私有模型版本与维护窗口。
- 导出、后台任务和更完整的模型能力验证。

### P3：体验、性能与工程质量

- 多实例高可用、Redis/PostgreSQL 高可用、备份恢复演练。
- 生产 TLS、WAF、网络隔离和自动密钥轮换。
- LiteLLM、数据库、Redis、队列和链路追踪监控。
- 同版本镜像、真实请求形态、长连接和流式负载的正式压测。
- CI 中加入配置 lint、Secret 扫描、迁移测试、故障注入和回归矩阵。

## 9. 推荐实施顺序

`需求与权限契约` → `安全与可复建部署` → `统一调用身份` → `管理服务与业务 Schema` → `SSO/组织/Key` → `模型渠道发布` → `额度账本` → `路由与 Fallback` → `日志审计与看板` → `管理后台` → `OAuth/内容审计/帮助中心` → `HA、备份、压测和上线演练`
