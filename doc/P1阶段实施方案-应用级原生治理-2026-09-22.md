## 1. 本次确认与设计结论

P1 不采用“同一把 Key 同时登记为 Higress Consumer Key 与 LiteLLM Virtual Key”的方案。客户端一旦获得可被 LiteLLM 接受的 Key，LiteLLM 端口或内部网络意外可达时，就可能绕过 Higress 的 Host、IP、入口认证、WAF 和入口审计。因此：

- 客户端始终只持有 **Key-H**（Higress Consumer Key）；
- LiteLLM 只接受 **Key-L**（LiteLLM Virtual Key）；Key-L 绝不返回给客户端；
- 每个应用有稳定、不可复用的 `app_id`，对应一个 Higress Consumer 与一个 LiteLLM Virtual Key；
- P1 不建立“随机 Key-L 明文 + 加密映射表”，而由一个仅内网可达的无状态映射组件按 `app_id` 使用 HMAC 稳定派生 Key-L；
- P1 不建立组织、用户、Team、Token 钱包、计费或第二套模型/额度系统。LiteLLM Virtual Key 是应用模型权限、RPM、TPM、并发与 SpendLog 的唯一业务权威。

这保留了 Key-H 与 Key-L 的安全隔离，也移除了本可避免的映射数据库、Key-L 明文持久化、Team 管理和自研审计表。

## 2. 首个验收目标与明确范围

### 2.1 首个验收目标

> 管理员可以为不同客户端应用独立开通、禁用、轮换 Higress API Key，并为每个应用设置可用模型、RPM、TPM、最大并发；客户端只使用 Higress Key，LiteLLM 按应用分别执行模型权限和调用策略。

最小验收对象为两个测试应用 `app-a`、`app-b`。两者必须能被 LiteLLM 稳定区分，策略、日志和拒绝结果不得互相影响。

### 2.2 本阶段包含

- 独立 P1 Docker 测试环境与 P0 回归保护。
- 每个应用一个不可变 `app_id`、一个 Higress Consumer、一把或短暂两把 Key-H、一个 LiteLLM Virtual Key（Key-L）。
- 已认证 Consumer 到 Key-L 的 HMAC 无状态精确映射。
- LiteLLM Virtual Key 原生的 `models`、`rpm_limit`、`tpm_limit`、`max_parallel_requests`、禁用和 SpendLog。
- 管理员使用受控 PowerShell CLI 完成应用策略调整、禁用、恢复、对账、Key-H 双凭证轮换和应用创建事务；持久化测试应用已完成全 P1 容器重启后的调用验证，App A 和持久化应用的同声明重复执行均已验证幂等。
- 映射伪造、服务故障、直连绕过、策略隔离、P0 回归的真实端到端验收。

### 2.3 本阶段明确不做

- 组织、学院、部门、用户、SSO、OAuth、RBAC、申请流和管理后台。
- LiteLLM Team。P1 的“一个应用一个 Virtual Key”已覆盖所需策略，Team 只会引入多一层状态和同步工作。
- 自研 Token 钱包、充值、账单、财务结算、发票或第二套 Token/额度账本。
- 模型单价未确认前的 `max_budget` 金额拦截；只保留 LiteLLM 的 Token/估算 Spend 记录。
- 复杂多模型自动路由、跨 Provider Fallback、会话粘性。
- 生产域名、生产 CIDR、生产 KMS/密钥托管实施。

这些内容不阻塞 P1 的应用级治理；生产网络、密钥治理、Audit 授权和定价统一按 [P0/P1 上线前决策清单](P0上线前决策清单-2026-09-22.md) 在服务器切换前关闭。

## 3. P0 现状、P1 缺口与不可复用方案

### 3.1 P0 已验收调用链

```text
客户端 / CCSwitch（Higress Consumer Key）
  -> Higress key-auth 验证
  -> Higress ai-proxy 注入统一 LiteLLM Master Key
  -> LiteLLM 依据逻辑模型选择 Provider Key
  -> 上游模型
```

P0 的 `ai-proxy` 对所有调用固定注入 `P0_LITELLM_MASTER_KEY`：

- [config/higress/p0-test/resources.json](../config/higress/p0-test/resources.json)
- [config/litellm.yaml](../config/litellm.yaml)

这正确完成了入口认证、Provider Key 隔离、基础限流、日志、SSE、Responses、工具调用与回滚；但 LiteLLM 只能看见统一 Master Key，不能可靠按 Higress Consumer 执行应用级模型权限、RPM、TPM、并发或 SpendLog 归属。

### 3.2 三种不能作为身份映射的现有能力

| 能力 | 实际作用 | 不能解决的问题 |
|---|---|---|
| Higress `ai-proxy.modelMapping` | 请求模型名到上游模型名的改写 | 不是 `Consumer -> Key-L` 身份映射。P1 不新增 Higress 模型改写，授权仍由 LiteLLM 判断。 |
| Higress `ai-proxy.apiTokens` 多值 | 普通请求随机选 Token；状态接口按哈希亲和 | 不能一对一选中指定 Key-L，可能碰撞，禁止用于应用授权。 |
| Higress `transformer` | 固定头删除、重命名、改写 | 不能按 Consumer 查询/派生不同 Key-L。 |

因此，Higress 与 LiteLLM 之间仍需要一个最小的身份转换点；但这个点不需要数据库、模型服务或计费服务。

## 4. 固定职责边界与原生能力复用

| 能力 | 权威执行点 | P1 复用方式 | 不新增的内容 |
|---|---|---|---|
| 客户端 API Key、Host、TLS、CIDR、WAF、请求尺寸、入口拒绝 | Higress | `key-auth`、现有入口策略、`ai-statistics` | 第二个客户端认证系统 |
| Key-H 多 Key 兼容与轮换 | Higress `key-auth` | 同一个稳定 Consumer 的 `credentials: [old, new]` | 新建旧/新两个 Consumer 或 Key-L 双配对 |
| Consumer 到 LiteLLM 身份转换 | 极小内部 mapper | `key-auth` 产生可信 Consumer，`ext-auth` 白名单注入上游头 | 映射表、随机 Key-L 明文保存、映射数据库 |
| 逻辑模型、Provider Key、协议适配、上游调用 | LiteLLM | 继续使用 `config/litellm.yaml` 和已有模型配置 | Provider Key 回迁 Higress |
| 模型白名单、RPM、TPM、最大并发、禁用 | LiteLLM Virtual Key | `/key/generate`、`/key/update`、`/key/block`、`/key/unblock` | Higress 再维护每应用业务限额 |
| Token、Spend、调用正文、用量日志 | LiteLLM SpendLog | 复用 P0 `store_prompts_in_spend_logs`、7 天本机清理 | 自研 Token/Spend/正文日志库 |
| 操作审计 | LiteLLM Audit + Higress 配置发布快照 | 验证并开启 LiteLLM 原生 Audit；复用 P0 发布快照/回滚证据 | 自建审计业务表 |
| 全局容量保护、入口攻击防护 | Higress | 请求大小、连接与明显高于业务阈值的兜底 | 复制 LiteLLM 的每应用业务额度 |

Higress 自带 `ai-quota`、`ai-statistics` 与 Consumer 限流。P1 复用 `ai-statistics` 做入口观测；不将 `ai-quota` 用为 P1 主业务额度，否则会出现 LiteLLM 与 Higress 两套额度状态、两套拒绝口径。若后续产品明确需要“按原始 Token 发放月额度”，再单独验证 `ai-quota` 对 Chat、Responses、SSE、Tools 的协议覆盖后决定是否引入。

## 5. Key 模型、派生规则与目标调用链

### 5.1 凭证边界

| 凭证 | 持有者 | 用途 | 客户端可见 |
|---|---|---|---:|
| Key-H | 应用、Higress | Consumer 认证与入口策略 | 是 |
| Key-L | 内部 mapper、LiteLLM | Virtual Key 模型/用量策略 | 否 |
| Provider Key | LiteLLM | 调用实际模型 | 否 |
| LiteLLM Master Key | LiteLLM 管理面、受控运维 CLI | 管理 Virtual Key | 否 |
| `P1_KEY_DERIVATION_SECRET` | mapper、受控运维恢复流程 | 派生所有 Key-L | 否 |

客户端只配置测试网关地址（例如 `http://ai-gateway-p1-test.local:18080`）和 Key-H。CCSwitch 或普通 OpenAI 客户端会基于地址自动生成 `Host`；客户端不需要额外设置特殊 Host。

### 5.2 稳定 Consumer 与无状态 Key-L 派生

创建应用时生成不可变、不可由显示名称替代的 ID，例如 `app-<UUID>`。它同时是 Higress Consumer 名称、LiteLLM `key_alias` 和 mapper 的唯一输入；应用显示名只是元数据。

```text
Key-L = "sk-" + Base64UrlNoPadding(
  HMAC-SHA256(
    P1_KEY_DERIVATION_SECRET,
    UTF8("campus-ai-gateway/litellm-key/v1/" + app_id)
  )
)
```

- `P1_KEY_DERIVATION_SECRET` 为独立、随机、至少 256-bit 的测试环境密钥，只通过 Docker secret 或未纳入 Git 的环境文件提供；不得复用 P0 Master Key、Provider Key 或生产密钥。
- `Base64UrlNoPadding` 结果固定，故 mapper 在每次请求无需读取数据库就能得到同一把 Key-L；`sk-` 前缀满足 LiteLLM 客户端指定 Virtual Key 的格式要求。
- 创建时，受控 CLI 用派生结果调用 LiteLLM `/key/generate`（显式传入 `key`），并设置 `key_alias=app_id`、`key_type=llm_api`、非空 `models` 与策略字段。LiteLLM 仍只保存其 Key Hash；mapper 不保存 Key-L。
- Key-H 与 Key-L 的值必然不同，且轮换 Key-H 不影响 Key-L、历史 SpendLog 或 LiteLLM 策略归属。

### 5.3 目标调用链

```text
客户端应用 A（仅 Key-H-A）
  -> P1 Higress
       1. 清理客户端伪造的内部身份/认证头
       2. key-auth 校验 Key-H-A，写入可信 Consumer = app-<uuid-A>
       3. ext-auth 调用仅内部可达的 mapper
       4. mapper 校验 allowlist，并按 Consumer HMAC 派生 Key-L-A
       5. 仅以 ext-auth 白名单控制的内部 `Authorization: Bearer Key-L-A` 向上游传递
       6. P1 专用 ai-proxy（无静态 `apiTokens`）复用标准 Authorization 转换逻辑
  -> LiteLLM 以 Key-L-A 执行 Virtual Key 策略并写 SpendLog
  -> Provider / 内网 my-qwen3.6-27b
```

mapper 是无状态的身份转换器，不是第二个 AI 网关：不处理模型、Token、计费、组织、Provider 或请求正文；不对客户端或宿主机发布端口。P1 仅允许 Higress 所在的内部 Docker 网络访问它；P1-0 要确认 `ext-auth` 到 mapper 的调用面不能被其他入口伪造。mapper 验证 Consumer 是否在无敏感信息的 allowlist 中，并只返回一个受 `ext-auth` 白名单限制的内部 `Authorization` 请求头；该头不会进入客户端响应。不能映射、无 allowlist、异常或超时都必须拒绝请求，绝不回退 P0 Master Key。

## 6. P1-0 技术闸门：先证实原生链路

2026-09-23 本地 Docker 实测结果见 [P1-0技术闸门验收-2026-09-23.md](P1-0技术闸门验收-2026-09-23.md)，结论为 `PASS`。实测发现不应再配置一个“认证后删除 Authorization”的 Transformer：ext-auth 成功后会用受白名单控制的标准 `Authorization: Bearer Key-L` 覆盖客户端 Key-H，额外删除插件会把 Key-L 一并删除，导致 LiteLLM 收到 401。当前 P1 资源已移除该插件。

先用两组测试 Consumer 与两把测试 Virtual Key，在独立环境验证：

- 实际运行镜像中 `key-auth -> ext-auth -> ai-proxy` 的插件顺序；特别是容器实际具备的 `ext-auth 2.0.1`、`ai-proxy` 版本，禁止只根据 vendored source 判断。
- 在 `key-auth` 之前清除客户端提供的 `X-Mse-Consumer`、`x-hi-original-auth`、`x-gateway-*`、mapper 内部认证头；认证成功后只能信任 Higress 写入的 Consumer。
- `ext-auth` 仅允许 mapper 返回指定上游头；Key-L 绝不能在响应头、响应体、日志、验收输出中返给客户端。
- P1 专用 `ai-proxy` 不配置 P0 静态 Master Key 或任何静态 `apiTokens`；验证 ext-auth 注入的标准 Authorization 能使 LiteLLM 只收到 Key-L。
- mapper 宕机、超时、Consumer 不在 allowlist、LiteLLM 未创建对应 Virtual Key 时均失败闭合，且不退回 P0 Master Key。
- 客户端伪造内部头不能获得其他应用身份；LiteLLM 推理与管理端口不能成为客户端或宿主机未授权绕过入口。
- A/B 请求在 LiteLLM SpendLog 中分别归属到各自 Key-L/`key_alias`，绝不显示 Master Key。

任一项不通过，停止在技术闸门，只评估最小自定义 Higress WASM 插件；**不得**降级为同一把 Key 双登记、多 Key `apiTokens` 或 Consumer 哈希亲和。

## 7. 工作包与实施顺序

### P1-0：隔离环境与无状态映射技术闸门

**目标**：不改 P0，证明 HMAC 双 Key 映射可用、不可绕过。

**主要工作**：

- 从 P0 Docker 组合克隆独立 P1 项目名、网络、卷、环境文件、测试域名与端口；不得挂载 P0 卷或复用 P0 密钥。
- 生成独立的 `P1_KEY_DERIVATION_SECRET`、`app-a`/`app-b`、Key-H 与对应 Key-L；仅由本机受控 CLI 生成，不在命令输出或报告中显示 Key-L。
- 用内网 `my-qwen3.6-27b` 做真实 Chat、SSE、Responses、Tools 请求；用未授权模型别名验证拒绝。
- 验证第 6 节的全部安全条件，并执行 P0 全量回归。

**完成标准**：A/B 在 LiteLLM 中归属不同 Virtual Key；策略不串扰；伪造、mapper 故障、LiteLLM 直连均失败；P0 回归通过。

**风险**：插件执行顺序、内部头覆盖或运行镜像版本可能不符合预期。风险未关闭前不建设管理 CLI。

### P1-1：无状态 mapper 与非敏感应用清单

**目标**：以最少自定义代码建立精确、可审核的 Consumer -> Key-L 转换。

**主要工作**：

- 实现无状态 mapper：读取 `P1_KEY_DERIVATION_SECRET` 与不含密钥的 `app_id` allowlist；严格规范化并匹配 Consumer 后派生 Key-L。
- mapper 不接数据库、不接 LiteLLM Master Key、不记录请求正文/Authorization/派生值；以健康检查和最少结构化安全日志运行。
- 应用清单只保存 `app_id`、显示名、状态、LiteLLM `key_alias`、策略版本等非敏感字段；Key-H 仅在 Higress Consumer 的 secret 配置中，Key-L 永不落盘。
- 固定一个 Key-L 派生算法版本 `v1`，测试向量写入测试代码；算法或编码任一变化都必须显式升级版本，禁止隐式变更。

**完成标准**：任意受信任 Consumer 都能稳定得到且仅得到自己的 Key-L；mapper 重启后结果不变；未在 allowlist 的 Consumer 严格拒绝；仓库、日志、报告和清单均无 Key-L/派生根密钥。

**风险**：根密钥保护成为集中安全边界；其缓解与恢复预案见第 9 节。

### P1-2：复用原生 API 的最小管理闭环

**目标**：管理员不手改运行 YAML，也能安全管理应用与原生 LiteLLM 策略。

**涉及模块**：受控 PowerShell CLI、P0 现有配置快照/回滚模式、Higress Consumer 配置发布、LiteLLM `/key/*` API、应用清单。

**主要工作**：

- 提供 `New-P1Application`、`Get-P1Application`、`Set-P1ApplicationPolicy`、`Disable-P1Application`、`Enable-P1Application`、`Rotate-P1HigressKey`、`Reconcile-P1Application`。
- 创建按顺序：生成稳定 `app_id` 与 Key-H；按规则派生 Key-L；通过 `/key/generate` 创建 Virtual Key；写入非敏感清单；将 Key-H 发布为 Higress Consumer；仅向管理员一次性展示 Key-H。
- 策略调整只调用 LiteLLM `/key/update`，至少显式设置非空 `models`、RPM、TPM、最大并发与状态；禁止“空 models = 所有模型”。
- 禁用先移除/失效 Higress Key-H，再 `/key/block` Key-L；恢复时先确认 LiteLLM Key 状态和策略，再发布 Higress Key-H。所有操作支持幂等重试、补偿和对账。
- 复用 P0 Higress 配置发布的快照/回滚证据；验证 LiteLLM 原生 `/audit` 能记录 Key 生命周期操作，并对敏感字段脱敏。

**完成标准**：两个应用经一组受控命令可创建、查询、改策略、禁用、恢复和对账；失败不产生未知有效凭证；CLI、日志、Git 无任何 Key 明文。

当前实现状态：`scripts/Manage-P1Application.ps1` 已支持 `Get`、`SetPolicy`、`Disable`、`Enable`、`Reconcile`、`RotateKeyH`、`RetireKeyH`；`scripts/New-P1Application.ps1` 已补齐应用创建、真实请求验证、失败补偿和 `-RollbackAfterVerify` 验收模式。应用创建事务已通过真实 Qwen 请求的成功验证与回滚；仍需补做一次保留式成功创建和同声明重复执行。运行时 Higress 资源由 `Snapshot-P1Higress.ps1`、`Publish-P1Higress.ps1`、`Rollback-P1Higress.ps1` 管理，原始快照只落在被忽略的 runtime 目录。

**风险**：Higress 配置发布与 LiteLLM 管理 API 非同一事务。以清单、幂等 ID、补偿步骤和 `Reconcile` 处理，不假设原子成功。

### P1-3：LiteLLM 原生应用策略与用量归属

**目标**：由 LiteLLM 成为模型权限与调用策略的唯一业务权威。

**主要工作**：

- 分别为 A/B 配置并验证 `models`、`rpm_limit`、`tpm_limit`、`max_parallel_requests`、有效期和 blocked 状态。
- 用真实 Chat、SSE、Responses、Tools 验证所有路径都以 Key-L 归属；未授权模型、超 RPM/TPM/并发必须在上游前失败。
- 从 LiteLLM SpendLog 获取 Key/模型/Token/耗时/结果；沿用 P0 `store_prompts_in_spend_logs` 与本机 7 天清理，不建设第二份业务日志。
- Higress 只保留请求大小、WAF、连接保护和明显高于业务阈值的全局防护，不复制每应用 LiteLLM 限额。

**完成标准**：A/B 模型权限、速率、并发、禁用和日志归属互不影响；流式和非流式均有证据。单价未确认时不设置 `max_budget`，Spend 不作为财务结算。

审计边界：P1 已按复用原则打开 LiteLLM 原生 `store_audit_logs`，但本地镜像的 `LiteLLM_AuditLog` 写入还受 `premium_user` 条件限制；在本地未取得审计行前，不把该能力计为完成，也不新增第二套自定义审计库。生产上线前必须确认所用 LiteLLM 版本/授权的原生 Audit 可用性和字段脱敏。

当前实测：已完成未授权模型拒绝和 App B RPM=1 时连续请求 `200/429` 的原生限流证据；新增 `scripts/Test-P1ProtocolMatrix.ps1`，已实际通过 TPM=1 的 429、max_parallel `[429,200]`、SSE、Responses、Tools 和 SpendLog（报告 `runtime/p1-test/reports/p1-protocol-matrix-20260923-104258.md`）。LiteLLM 本地镜像的原生 Audit 仍受 `premium_user` 授权条件限制，未把它标记为完成，也未新增第二套审计表。

**风险**：上游/协议可能在流式结束未回传完整 usage；验收应将“策略是否拒绝”与“usage 是否完整”分开判定。

### P1-4：Key-H 轮换、禁用与恢复演练

**目标**：复用 Higress 原生多凭证能力，以最小状态和最小暴露完成客户端 Key 轮换。

```text
稳定 app_id / Consumer
  旧：credentials = [Key-H-1]              -> 固定 Key-L
  窗口：credentials = [Key-H-1, Key-H-2]    -> 同一固定 Key-L
  完成：credentials = [Key-H-2]             -> 同一固定 Key-L
```

**主要工作**：

1. 为原 Consumer 生成 Key-H-2，配置 `credentials: [Key-H-1, Key-H-2]`，不改变 `app_id` 和 Key-L。
2. 只向管理员展示 Key-H-2；用真实调用验证其仍被映射到原 Virtual Key 与原策略。
3. 在记录责任人与截止时间的短窗口内兼容两把 Key-H。
4. 窗口结束后移除 Key-H-1，验证旧 Key 经 Higress 失败；无需也不得轮换 Key-L。
5. 禁用演练：先阻断 Key-H，后 block Key-L；恢复按 P1-2 受控顺序执行。

**完成标准**：窗口内两把 Key-H 均仅代表同一个应用和同一 Key-L；窗口后旧 Key 无法调用；没有无归属请求、无 Key-L 泄露，且可通过发布快照回滚。

当前实测：`Manage-P1Application.ps1 -Action RotateKeyH` 已实现双凭证窗口，`-Action RetireKeyH -RestartHigress` 已实测旧 Key-H 返回 401、新 Key-H 返回 200。实测还发现仅调用 Higress 管理 API 删除 credential 不能保证运行中 key-auth 插件立即清缓存，因此退休动作强制要求显式重启；生产应替换为有健康检查和连接摘除的滚动更新流程。

**风险**：窗口延长会增加旧 Key 暴露时间。必须设置最大窗口、责任人和强制撤销时间。Key-L 不做常规轮换的风险与紧急处置见第 9.3 节。

### P1-5：端到端验收、观测与结项

**目标**：以真实请求而非“配置存在”证明 P1 可用。

**主要工作**：

- LiteLLM 是 Token、估算 Spend、模型、Virtual Key 归属的主证据；Higress `ai-statistics` 保留入口 QPS、状态码、延迟、拒绝与安全事件。
- LiteLLM Audit、Higress 发布快照和 CLI 脱敏操作记录共同组成操作证据；不另建审计数据库。
- 延续 P0 正文记录：仅本机测试数据库保留 7 天、不得提交仓库；生产留存期与访问权限另行决策。
- 执行第 8 节矩阵并输出 `PASS`、`FAIL`、`SKIP`、`UNKNOWN`；未知能力不写为通过。

## 9. HMAC 派生方案的风险评估与处置

### 9.1 结论

该方案在 **本地独立 P1 环境** 是推荐最小实现：它消除每应用 Key-L 明文、密文映射库、Team 与额外审计表，却仍确保客户端的 Key-H 不能直接作为 LiteLLM Key 使用。风险没有消失，而是集中到派生根密钥、Higress 到 mapper 的可信头链路与 Key-L 紧急恢复流程；这些必须在 P1 验收和服务器上线前分别关闭。

### 9.2 风险清单

| 风险 | 影响 | P1 控制措施 | 上线前要求 |
|---|---|---|---|
| `P1_KEY_DERIVATION_SECRET` 泄露 | 攻击者可推导全部应用 Key-L；若可直连 LiteLLM，影响面为全体应用 | 仅 Docker secret/未纳管环境文件；最小权限；泄露扫描；LiteLLM 不对客户端暴露 | 使用运维确认的 Secret/KMS，限制读取主体，演练全量恢复 |
| 单个 Key-L 泄露 | 可绕过 Higress，以该应用身份调用 LiteLLM（前提是 LiteLLM 可达） | Key-L 不回传、无日志、无持久化；LiteLLM 仅内部网络可达 | 监控异常直连；具备隔离、block 与替换流程 |
| Key-L 不支持常规单应用轮换 | HMAC 无状态派生不能无状态地产生同一 `app_id` 的第二把独立 Key-L | P1 将常规轮换限定为 Key-H；Key-L 从不分发给客户端 | 生产确定是否接受，或引入 KMS 加密映射/派生版本状态 |
| 根密钥轮换 | 更换根密钥会改变所有 Key-L，不能只改环境变量 | P1 测试环境记录恢复 Runbook，不把“改根密钥”当日常操作 | 制定批量新建 Virtual Key、复制策略、切换 mapper、撤销旧 Key 的演练方案 |
| 内部 Consumer 头伪造/插件次序错误 | 攻击者可能请求到错误 Key-L | P1-0 验证先删头再 key-auth，再 ext-auth；mapper allowlist；失败闭合 | 固定镜像版本/配置校验，变更后回归安全用例 |
| mapper 或 ext-auth 不可用 | 所有 P1 流量失败 | 健康检查、短超时、失败闭合、明确告警；P0 不受影响 | 高可用、容量与故障转移设计 |
| 非 Higress 工作负载调用 mapper | 若其可伪造 Consumer 头，可能获得 Key-L | 不发布 mapper 端口，限制为独立内部网络；P1-0 用直连请求验证拒绝 | mTLS 或等价服务认证、网络策略与调用方身份审计 |
| LiteLLM 直连暴露 | Higress 的 IP/WAF/审计被绕开 | 本地只 internal network；不发布 LiteLLM 端口；直连验收 | 服务器网络策略和监听地址验收，管理面另行隔离 |
| HMAC 算法实现漂移 | 重启或升级后派生出不同 Key-L，造成全量调用失败 | 固定域分隔字符串、编码、无填充规则和测试向量；版本 `v1` | 变更走显式版本迁移，不能静默升级 |
| 启用/禁用跨系统非原子 | Higress 与 LiteLLM 状态短暂不一致 | 受控顺序、幂等命令、补偿、`Reconcile` 与发布快照 | 纳入运维 SOP、告警和定期对账 |
| P1 无组织/RBAC | 管理 CLI 操作权限过大 | 本地仅指定管理员/本机使用，CLI 不对网络发布 | P2 前确定 SSO/RBAC、审批和最小权限 |

### 9.3 Key-L 事件处置边界

P1 的 Key-L 不对客户端分发，正常情况下不应轮换。若怀疑单个 Key-L 泄露，立即：

1. 从网络侧确认 LiteLLM 无外部可达路径，并用 `/key/block` 阻断该 Virtual Key；
2. 关闭对应 Higress Consumer，防止正常入口继续计费或产生混淆；
3. 对本地测试环境，可新建新的 `app_id`/Consumer/Key-H/Virtual Key，复制已审核策略后切换客户端；旧应用保持 block 并保留审计证据；
4. 不得为了“快速恢复”把 Key-H 与 Key-L 设为同值，也不得将 Key-L 输出给客户端；
5. 若派生根密钥泄露，按“全量根密钥轮换”事件处理，而非仅 block 单一 Key。

这也是该无状态方案相对“加密随机 Key-L 映射”的主要取舍：更少的日常状态与攻击面，交换为更重的 Key-L 泄露恢复。生产若不接受这一取舍，应在服务器上线前改为 KMS 加密的随机 Key-L 映射，而不是在 P1 中暗中增加明文表。
