## 1. P0 最终定位

P0 采用当前已经验证的访问模型，不改变客户端接入方式：

```text
CCSwitch / 其他客户端
  → Higress Consumer Key
  → Higress Host 路由、认证和边缘治理
  → Higress 注入内部 LiteLLM Master Key
  → LiteLLM 选择逻辑模型和 Provider Key
  → 上游模型
```

P0 的目标不是建设完整校园管理平台，而是完成一条安全、可复现、可验收的统一模型调用链。

P0 完成后，平台应能够：

1. 客户端只需要一个 Higress Consumer Key 和一个统一服务地址。
2. Higress 能正确匹配正式 AI 路由并拒绝非法请求。
3. LiteLLM 能稳定代理已验证模型，并使用各模型对应的上游 Provider Key。
4. LiteLLM 能记录 Token、Spend、模型、耗时和请求结果。
5. Higress 能提供基础限流和入口监控；IP 控制等待运维批准 CIDR 后启用，模型 Token/Spend 由 LiteLLM 原生记录。
6. 配置、密钥、镜像和运行环境可以从仓库重新构建。
7. 组织、SSO、部门/课题组、财务级账本和复杂管理后台暂不作为 P0 前置条件。

## 2. 已固定的架构决策

### 2.1 客户端凭证

客户端使用 Higress Consumer Key，不直接使用 LiteLLM Virtual Key。

CCSwitch 当前应使用：

```text
请求地址：http://ai-gateway-test.local:18080
API Key：Higress Consumer Key
```

在开发机上使用 hosts 或 DNS 将域名解析到网关地址，例如：

```text
192.168.31.113 ai-gateway-test.local
```

客户端最终发送的请求必须满足：

```http
POST http://ai-gateway-test.local:18080/v1/chat/completions
Host: ai-gateway-test.local
Authorization: Bearer <Higress Consumer Key>
```

如果使用 IP 地址访问，Host 会变成 IP，不能命中当前按域名匹配的 AI 路由。CCSwitch 应使用 `ai-gateway-test.local:18080`；未配置 hosts/DNS 时，验收脚本可显式指定正确 Host。

### 2.2 Higress 的职责

Higress 负责客户端到平台入口这一段：

- Host、域名和 `/v1` 路由匹配；
- TLS 终止；
- Higress Consumer Key 认证；
- 路由级 Consumer 授权；
- IP 白名单/黑名单；
- 基础请求限流和并发保护；
- WAF、请求大小、超时等入口治理；
- request_id 和入口访问日志；
- AI Token、首 Token 延迟、总耗时等基础统计；
- 将请求转发到 LiteLLM。

Higress 不负责：

- Provider API Key 管理；
- Provider 协议转换；
- 模型别名到上游模型的主要映射；
- LiteLLM SpendLog 写入；
- 组织树、学校 SSO 和财务账本。

### 2.3 LiteLLM 的职责

LiteLLM 负责模型代理和上游模型调用：

- Chat Completions、Responses、Embeddings 等协议适配；
- 逻辑模型名到 Provider 模型名的映射；
- Provider API Key 读取与上游调用；
- 上游错误转换；
- 输入/输出/总 Token 统计；
- Spend 估算；
- 模型、请求、耗时和用量日志；
- LiteLLM 内部 Master Key 认证；
- 已配置的模型路由和 Provider 选择。

LiteLLM 的 Virtual Key、Team、Budget 能力继续保留，但不作为当前 P0 客户端凭证体系。后续如果需要按 Consumer 独立预算，再增加 Consumer 与 LiteLLM Team/Virtual Key 的映射。

### 2.4 项目自有代码的职责

P0 只保留必要的项目代码：

- Compose 和配置模板；
- Secret 注入和配置校验；
- Higress/LiteLLM 启动与就绪检查；
- Qwen Responses 兼容补丁；
- LiteLLM 流式空 `choices` 补丁；
- 模型能力和 Provider Key 验证脚本；
- 端到端测试、限流测试和日志核对脚本；
- 配置版本、部署信息和回滚说明。

P0 不新增：

- 自定义 Key 验证服务；
- 自定义 Token 计费引擎；
- 自定义预算数据库；
- 自定义组织服务；
- 自定义路由代理；
- 自定义基础限流插件。

### 2.5 P0 网络代理决策

P0 明确采用 **全链路直连，不依赖代理**：

```text
CCSwitch → Higress：直连
Higress → LiteLLM：Docker 内网直连
LiteLLM → Provider：直连
```

当前运行中的 LiteLLM 容器已经核验为未设置 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 或 `NO_PROXY`，P0 不向 Compose 增加代理变量。

如果 CCSwitch 所在 Windows 启用了 v2rayN 系统代理，P0 验收时应临时关闭系统代理；若需要保留系统代理供其他软件使用，则在 v2rayN 路由规则中把 `ai-gateway-test.local`、网关 IP 和内网 CIDR 指定为 `direct`。这只是防止客户端误将内网网关流量转给代理，不代表模型调用需要代理。

## 4. P0 工作包

## P0-1：正式入口和访问方式固化

### 目标

让所有客户端使用同一个正式 Host 和路径，避免 IP 访问、默认路由、测试路由之间产生歧义。

### 修改内容

1. 将当前 `ai-test.local` 开发/验证域名统一迁移为 `ai-gateway-test.local`；生产环境另行替换为正式内网域名。
2. 为客户端提供 hosts/DNS 配置说明。
3. 在 CCSwitch 接入文档中明确：
   - 请求地址填写域名而不是 IP；
   - API Key 填 Higress Consumer Key；
   - 不携带自定义 Host 时不能命中 AI 路由。
   - P0 调用不需要代理；验证期间关闭 v2rayN 系统代理，或为 `ai-gateway-test.local`、网关 IP 和内网网段设置直连规则。
4. 将默认 `litellm-proxy` 路由标记为内部兼容入口或测试入口。
5. 明确 `/v1/models`、`/v1/chat/completions`、`/v1/embeddings` 为 P0 首批接口。

### 完成标准

- CCSwitch 使用域名即可完成模型列表和 Chat 调用。
- IP 访问和域名访问的路由差异有明确文档。
- 默认入口不会被误认为正式校园 AI 入口。
- 路由命中可以通过 Host、响应头和 Higress 日志确认。

### 风险

- 内部 DNS 或 hosts 未配置会导致客户端误以为 Key 无效。
- 生产域名、证书和当前测试域名需要在部署时切换。

## P0-2：Higress 入口安全加固

### 目标

确保正式 AI 路由在认证、插件或策略依赖异常时不会放行。

### 修改内容

1. `key-auth` 的 `failStrategy` 改为 `FAIL_CLOSE`。
2. `ai-proxy` 的 `failStrategy` 改为 `FAIL_CLOSE`。
3. 正式 AI 路由显式启用 Key Auth，不依赖全局默认配置。
4. 清除客户端伪造的内部身份 Header。
5. 设置可信代理链和真实来源 IP 获取规则。
6. 配置 IP Restriction，至少提供平台级允许/拒绝策略。
7. 限制管理端口 8001 的访问范围。
8. LiteLLM 4000 只允许 Higress 和管理网络访问。
9. PostgreSQL 只加入内部网络，不绑定宿主机公网端口。
10. Grafana 关闭匿名访问；Prometheus 不作为公网服务暴露。

### 完成标准

- 无 Key、错误 Key、错误 Host 均不能触达 LiteLLM 和上游。
- Key Auth 或 AI Proxy 加载失败时请求被拒绝。
- 外部网络不能直接访问 LiteLLM、PostgreSQL 和管理控制台。
- IP 拒绝返回 403，并带 request_id。

### 风险

- 改为 fail-closed 可能导致插件加载问题直接影响业务，因此必须先完成隔离环境回归。
- 可信代理链配置错误可能导致合法客户端被误拒绝或错误识别来源 IP。

## P0-3：凭证和部署配置治理

### 目标

消除明文测试凭证和浮动版本，使环境可以从仓库重新构建。

### 修改内容

1. 立即轮换已出现在仓库、运行配置和测试脚本中的：
   - Higress Consumer Key；
   - LiteLLM Master Key；
   - PostgreSQL 密码；
   - Provider API Key；
   - TLS 私钥和证书。
2. 通过 Secret Manager、Kubernetes Secret 或开发环境 `.env.local` 注入秘密。
3. `.env.example` 补齐当前模型配置实际使用的变量名：
   - `DASHSCOPE_API_KEY`；
   - `ZHILIN_aigc_API_KEY`；
   - `DEEPSEEK_API_KEY`；
   - `AGNES_API_KEY`；
   - `LITELLM_MASTER_KEY`；
   - 数据库连接变量。
4. 删除 Compose 中的默认 `sk-local-test` 和默认数据库密码。
5. 固定 Higress、Prometheus、LiteLLM 等镜像 digest。
6. 将 `runtime/` 中的配置整理为：
   - 脱敏模板；
   - 初始化脚本生成物；
   - 运行态导出目录。
7. 增加 Secret 扫描和 YAML/Compose 校验。

### 完成标准

- 新环境不依赖旧机器上的 `runtime/`、Docker 卷或人工记忆配置。
- 仓库和构建日志中不存在明文凭证。
- 镜像、配置哈希、部署时间和补丁版本可查询。
- 缺少必要 Secret 时服务明确失败，而不是使用默认值启动。

### 风险

- 轮换 Key 会使现有 CCSwitch 配置失效，需要安排切换窗口。
- 当前运行时证书和凭证可能被其他本地测试脚本依赖，轮换前要同步更新验证脚本。

## P0-4：LiteLLM 模型和 Provider Key 验证

### 目标

确认模型配置、Provider Key、协议和能力真实可用，不把模型列表返回成功误判为所有模型可用。

### 修改内容

逐模型验证：

| 模型 | 必测能力 |
|---|---|
| `my-kimi-k2.7-code` | Chat、非流式、编码提示词 |
| `my-qwen3.5-ocr` | Chat、图片输入、OCR |
| `qwen3.7-flash` | Chat，并核对实际 Provider 模型是否应为 OCR |
| `my-qwen3.7-text-embedding` | Embeddings、向量维度、批量输入 |
| `my-qwen3.6-27b` | Chat、Responses、流式、工具调用兼容范围 |
| `my-deepseek-v4-flash` | Chat、流式、usage |
| `my-agnes-2.5-pro` | Chat、流式 |
| `my-agnes-image-2.5-flash` | Images、图片结果格式 |

每次测试记录：

- 客户端请求地址和 Host；
- Higress Consumer Key 是否通过；
- 逻辑模型名；
- 实际 Provider 模型名；
- 接口类型；
- 是否流式；
- HTTP 状态码；
- request_id；
- 输入/输出/总 Token；
- Spend；
- 首 Token 延迟和总耗时；
- 失败原因。

P0 首个真实验收模型固定为 `my-qwen3.6-27b`。它是校内部网部署模型，优先用于验证以下整条真实链路：

```text
CCSwitch → ai-gateway-test.local → Higress Consumer Key → AI Proxy → LiteLLM → 校内 Qwen3.6-27B
```

先通过该模型完成入口认证、Host 路由、非流式、流式、Responses、Token、SpendLog、request_id、异常和回滚验证，再逐项扩展到外部 Provider 模型。

### 完成标准

- `/v1/models` 返回的模型均有对应验证状态。
- Provider Key 错误时能区分为上游认证错误，而不是普通 500。
- 模型别名错误或 Provider 模型不存在时能定位。
- 已声明支持的 Chat、流式、Embeddings、Images、Responses 能力逐项有证据。
- `qwen3.7-flash` 的配置问题得到明确结论并修正或记录为别名规则。

### 风险

- 真实 Provider 调用可能产生费用。
- 不同 Provider 对 Responses、工具调用和图片格式的支持不同，不能仅依赖 OpenAI 兼容声明。

## P0-5：LiteLLM Token、Spend 和日志验收

### 目标

确认 LiteLLM 原生计量能力可作为 P0 的平台用量统计来源，不重复开发计费引擎。

### P0 采用的口径

P0 使用 LiteLLM 的：

- 输入 Token；
- 输出 Token；
- 总 Token；
- Spend 估算；
- 模型维度；
- 时间维度；
- 请求耗时；
- LiteLLM SpendLog。

P0 暂不承诺：

- 部门费用分摊；
- 课题组费用分摊；
- 财务实际账单核对；
- 充值、结转和补偿；
- 每个 Higress Consumer 的独立余额；
- 真实 Provider 账单的一致性。

### 修改内容

1. 确认 `LiteLLM_SpendLogs` 的请求、模型、Token、Spend 和耗时字段持续写入。
2. 保持 `store_prompts_in_spend_logs: true`，复用 LiteLLM 内置的 Prompt/Response SpendLog 记录；验证 `proxy_server_request` 与 `response` 字段按预期写入。
3. 验证 LiteLLM 的请求净化与敏感字段脱敏行为：完整 API Key、Authorization、Provider Key 和 `secret_fields` 不得写入 SpendLog。
4. 为含正文日志明确本地测试环境保留期限和访问范围；生产环境上线前另行确认学校数据留存要求。
5. 检查流式请求结束事件是否写入完整 usage。
6. 检查 Provider 缺失 usage 时是否标记为未知或待核对，不填 0 冒充真实值。
7. 检查失败请求、上游 Key 错误、客户端取消和超时是否产生可解释日志。
8. 按 request_id 关联 Higress 访问日志和 LiteLLM SpendLog。
9. 验证一次请求不会产生重复 SpendLog 或重复计量。

### 关于 Higress Consumer 的计量归属

当前 AI Proxy 将客户端 Higress Key 转成同一个 LiteLLM Master Key。因此 LiteLLM 原生 Key/Team 预算不会自动按 Higress Consumer 区分。

P0 先接受以下统计范围：

- 平台总 Token；
- 平台总 Spend；
- 模型维度；
- Provider 维度；
- 时间维度；
- 请求结果和耗时。

如果后续需要按 Higress Consumer 独立计量，再评估：

1. 由 Higress 注入可信 Consumer 元数据；或
2. Higress Consumer 映射到 LiteLLM Team/Virtual Key；或
3. 使用 Higress AI Quota/Token Rate Limit 做 Consumer 级阻断。

这不是 P0 的前置条件。

### 完成标准

- 每次已完成模型调用均能在 LiteLLM SpendLog 找到。
- Token、Spend、模型和耗时字段可读取。
- 请求失败和流式取消不会静默丢失。
- SpendLog 默认保留 Prompt/Response 正文；日志中不出现完整 Key、Authorization、Provider Key 和其他凭证。
- 通过相同 request_id 或可靠关联字段完成 Higress 与 LiteLLM 对账。

## P0-6：Higress 原生治理能力配置

### 目标

优先使用 Higress 官方能力，避免重复实现基础网关治理。

### 优先使用的能力

| 能力 | 实现方式 | P0 是否启用 |
|---|---|---|
| Consumer Key Auth | `key-auth` | 是 |
| IP 控制 | `ip-restriction` | 是，至少平台级 |
| 请求限流 | `cluster-key-rate-limit` 或现有限流插件 | 先验证后启用 |
| AI Token 指标 | `ai-statistics` | 是 |
| Token 配额 | `ai-token-ratelimit` / `ai-quota` | 可选，需 Redis |
| WAF/请求保护 | Higress 原生插件 | 按部署环境启用 |
| Provider 协议适配 | LiteLLM AI Proxy | 由 LiteLLM 承担 |

### 限流权威点

P0 只能选择一种实际阻断口径：

- Higress 负责 Consumer 级 RPM/TPM/Token 配额；LiteLLM 只记录 Spend；或
- LiteLLM 负责 Virtual Key/Team Budget；Higress 只做入口保护。

由于当前客户端使用 Higress Key，P0 推荐先采用：

```text
Higress：认证、IP、RPM、基础并发和可选 Token 阻断
LiteLLM：模型调用、Token 统计、Spend 记录
```

不在两个组件中对同一额度重复扣减。

### 完成标准

- 正确 Consumer Key 可以调用；错误 Key 被拒绝。
- IP 拒绝返回 403。
- 超过限流阈值返回 429，并能区分 Higress 限流和上游 429。
- 插件依赖异常时不放行。
- AI Statistics 能采集输入 Token、输出 Token、首 Token 延迟和总耗时。

## 8. P0 风险和应对

| 风险 | 影响 | 应对 |
|---|---|---|
| DNS/Host 配置错误 | 客户端命中默认路由，误判 Key 无效 | 提供 hosts/DNS 和 curl 验证命令 |
| v2rayN 接管内网请求 | CCSwitch 请求进入代理，导致 DNS、Host 或连接异常 | P0 验收时关闭系统代理；长期使用时设置网关域名/IP/CIDR 为 direct |
| Consumer Key 泄露 | 未授权调用 | 立即轮换、短期有效期、IP 策略、审计 |
| Master Key 暴露 | 可绕过 Higress | LiteLLM 仅内网，Master Key 只放 Secret |
| 两层重复限流 | 错误 429、额度口径不一致 | 明确唯一阻断权威点 |
| Provider usage 缺失 | Spend/Token 不精确 | 标记未知或待核对，不填 0 |
| 上游重试造成重复调用 | 成本和副作用增加 | P0 关闭不必要重试，限定总尝试次数 |
| 浮动镜像升级 | 行为和补丁不一致 | 固定 digest，构建期回归 |
| 运行态配置未提交 | 无法复建和回滚 | 脱敏模板 + 初始化/导出脚本 |
| 外部 Provider 验证产生费用 | 测试成本 | P0 先使用内网 `my-qwen3.6-27b`；外部模型执行前提供每日/总预算和专用测试 Key |
